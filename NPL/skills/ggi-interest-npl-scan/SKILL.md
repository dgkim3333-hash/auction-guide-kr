# ⚠️ 반드시 지킬 것

### 1. 상세·문건접수는 `www.ggi.co.kr` 이다 ★★ (2026-09-14 호스트 이전 실측 — 최우선 확인)

**모든 페이지가 `www.ggi.co.kr` 단일 호스트에 있다.** 목록도, 토큰 발급도, 상세도, 문건접수 뷰어도 전부 같다.

#### 1-0. 호스트 대조표 — 같은 idcode·같은 토큰·같은 쿠키로 실측

| 호스트 | `/detail/scheduled?idcode=<실제>` | 판정 |
|---|---|---|
| **`www.ggi.co.kr`** | 본문 정상 렌더 | **이것만 쓴다** |
| `web.ggi.co.kr` | **무한 루프 · 렌더러 프리즈** | 옛 호스트. 절대 쓰지 않는다 |
| `ggi.co.kr` (apex) | **502 Bad Gateway** | 백엔드 없음 |

> ★★ **`web.ggi.co.kr` 을 쓰면 안 되는 이유가 "안 열려서"가 아니다.**
> 옛 호스트는 **제거되지 않고 껍데기 앱이 남아 있다.** 문서는 150ms 만에 200으로 돌아오고
> 화면만 비어 있다가, 실재하는 idcode를 만나면 데이터를 못 받아 **무한 리렌더에 빠진다.**
> 그 상태에서는 `Runtime.evaluate` 가 45초 타임아웃을 내고 탭이 통째로 죽는다.
> 2026-09-07 · 09-14 두 회차가 이것 때문에 **전건 미처리**로 끝났다.
>
> **오진 경보** — 이 증상은 「사이트 장애」·「로그인 만료」·「스크래핑 차단」처럼 보인다.
> 실제로 그렇게 3주를 낭비했다. **상세가 멈추면 원인 조사보다 호스트부터 확인한다.**
> 「스킬에 그렇게 적혀 있으니 호스트는 맞겠지」가 바로 그 3주의 원인이었다.

> **Chrome 주소창은 `www.` 를 숨긴다.** 화면에 `ggi.co.kr/detail/...` 로 보여도
> 실제 호스트는 `www.ggi.co.kr` 이다. 주소창을 눈으로 읽고 apex 라고 단정하지 않는다.
> 확인은 `location.hostname` 으로 한다.

#### 1-1. 토큰 절차 — 상세 페이지 전용

**근거** — 구버전 상세 팝업(`/wait/mulgun_detail_popup_w.asp`)의 인라인 함수 `new_waitdetail()` 원문.
사이트가 실제로 쓰는 흐름이므로 아래를 **그대로** 따르되, **호스트만 `www` 로 바꾼다.**

```js
fetch(`/api/login?idcode=<IDCODE>&setc=y`)
  .then(r => r.json())
  .then(data => {
    if (data.result) {
      location.href = "https://www.ggi.co.kr/detail/scheduled"
        + "?idcode=" + IDCODE
        + "&token="  + data.token
        + "&type="   + data.urlType
        + "&category=" + data.category;
    }
  });
```

> **적용 범위** — 토큰이 필요한 것은 **상세 페이지(STEP 3)뿐이다.**
> 목록 수집(STEP 1)은 구버전 ASP 엔드포인트를 쓰므로
> **세션 쿠키만으로 동작하고 토큰이 필요 없다.** 목록에 토큰 절차를 적용하지 않는다.

**절차**
1. `www.ggi.co.kr` 오리진에서 호출한다
   ```
   /api/login?idcode=<IDCODE>&setc=y
   ```
   `setc=y` 는 필수로 보인다. 의미는 소스에 없으므로 **원문 그대로** 넣고 임의로 빼지 않는다.

2. 응답 JSON 4개 키를 받는다 (2026-09-14 재확인: `result=true`)

   | 키 | 용도 |
   |---|---|
   | `result` | boolean. `false` 면 발급 실패 |
   | `token` | 서명 토큰(JWT). 앞에 `asp` 접두어가 붙어 온다 — 떼지 않고 통째로 쓴다 |
   | `urlType` | URL의 `type` 파라미터. **빈 문자열로 오는 경우가 있다** |
   | `category` | URL의 `category` 파라미터. **빈 문자열로 오는 경우가 있다** |

3. URL에 **4개 파라미터를 모두** 붙인다. 값이 비어 있어도 파라미터 자체를 지우지 않는다
   ```
   https://www.ggi.co.kr/detail/scheduled?idcode=<IDCODE>&token=<token>&type=<urlType>&category=<category>
   https://www.ggi.co.kr/detail/scheduled/viewer?idcode=<IDCODE>&tab=court-report&token=<token>&type=<urlType>&category=<category>
   ```

4. `data.result` 가 `false` 이거나 호출이 실패하면 그 사실을 보고하고, **구버전 상세**(3-0)로 등기부현황만 확보한 뒤 문건접수는 `[정보부족]`으로 처리한다

> **하지 말 것**
> - **`web.ggi.co.kr` 을 쓰는 것** — 탭이 죽는다 (1-0)
> - `ggi.co.kr` (apex) 을 쓰는 것 — 502
> - `token` 하나만 붙이고 `type`·`category` 를 생략하는 것 — 다른 물건에서 깨진다
> - 빈 문자열이라고 파라미터를 제거하는 "최적화"
> - `/api/detail/wait.asp` 등 추측한 경로를 쓰는 것 — 그런 엔드포인트는 없다
> - `idcode` 를 고정 규칙으로 만들어 내는 것. 반드시 목록 페이지의 실제 링크에서 읽는다

**구버전 `/wait/mulgun_detail_fileview.asp` 는 법원문건접수 조회 결과가 항상 0건이다.** 여기서 판단하지 않는다.

#### 1-A. 토큰 수명은 300초다 ★

발급된 JWT의 `exp − iat = 300`. **5분이면 만료된다.**

- **물건마다 상세를 열기 직전에 발급한다.** 목록을 먼저 훑으며 토큰을 모아두면 뒤쪽 물건은 전부 만료된 토큰을 쓴다
- 상세 페이지와 문건접수 뷰어는 **각각 새로 발급**한다. 두 페이지 사이에 분석이 끼면 5분을 넘긴다
- 한 물건 처리가 5분을 넘겼는데 다시 열어야 하면 **토큰부터 재발급**한다
- 만료 토큰으로 접속하면 백지가 뜬다. 이때 "데이터 없음"으로 판정하지 않는다 — 재발급 후 1회 재시도한다

#### 1-B. `fetch` 로는 상세 데이터를 못 얻는다 — 반드시 이동한다 ★

호스트가 `www` 로 통일되면서 **교차오리진 CORS 문제는 사라졌다.** 하지만 상세는 Next.js 클라이언트 렌더라
`fetch` 로 받으면 **껍데기 셸(약 55,000자)만 오고 물건 데이터가 없다.** 실제 페이지 이동이 필요하다.

**올바른 순서**
1. 목록 탭은 **읽기만** 한다. STEP 1 의 POST 로 idcode·그룹·채권자·청구액을 뽑고 그대로 둔다
2. **별도 탭**을 만들어 `www.ggi.co.kr` 오리진을 먼저 연다
3. 그 탭에서 토큰을 발급하고 `location.href` 로 상세로 이동한다
4. 물건이 끝나면 같은 탭을 다음 물건에 재사용한다

> 목록 탭과 상세 탭을 분리하는 이유는 이제 오리진 문제가 아니라 **목록 파싱 결과를 잃지 않기 위해서**다.
> 목록 탭에서 페이지를 이동하면 `window` 에 담아둔 파싱 결과가 통째로 날아간다.
> idcode 를 상세 탭으로 넘길 때는 같은 오리진이므로 `localStorage` 를 쓰면 된다.

> 새 탭은 생성 직후 `chrome://` 상태다. **먼저 `navigate` 로 www 오리진을 연 뒤** 스크립트를 실행한다.
> 빈 탭에서 바로 실행하면 `Cannot access a chrome:// URL` 로 실패한다.

#### 1-C. 토큰을 기록에 남기지 않는다

토큰은 **계정 ID가 들어간 JWT**다.
이력 JSON·로그·보고·산출물 어디에도 토큰 문자열을 적지 않는다. 발급 성공 여부(`result`)만 남긴다.
디버깅을 이유로 토큰을 주소창·보고문에 노출하지 않는다.

### 2. 등기부현황만 보고 판단하지 않는다
채권 양도·채무자 파산·임차인 배당요구는 **법원문건접수에만** 나타난다.

실측 사례 3건
- 부천9계 2026-30341 — 등기부 근저당 1건뿐인데 채권자변경신고서(2026.06.09) + 채무자·소유자 파산선고
- 수원13계 2025-1727 — 등기부 근저당 1건뿐인데 유동화전문회사 승계(2025.10.22)
- 수원13계 2025-1614 — 당사자내역에 승계인(유동화전문 유한회사) 등재

> **다만 등기부만으로 반려가 확정되는 경우도 있다.** 최선순위 근저당보다 **전입일이 앞선 임차권**이
> 등기부에 보이면 대항력 있는 선순위 임차인이므로, 문건접수를 못 열었더라도 그 자리에서 `rejected` 다.
> 실측: 수원12계 2026-758 — 근저당 2026.05.08 vs 임차인 전입 2021.05.31 · 보증금 240,000,000원.

> ★ **등기부는 「목록 N번」 한 건만 보여줄 수 있다.** 구버전 팝업의 등기부현황 하단에
> `[목록 N번의 등기임]` 표기가 있다. 매각목록이 여러 건이면 **그 한 건의 등기만 본 것**이다.
> 사건 전체의 담보를 그 한 건으로 판단하지 않는다 (STEP 3-1).

### 3. 즉시 반려 사유 — 발견 즉시 중단한다 ★

- **채권자변경신고서 · 승계인 등재 · 채권양도** — 이미 제3자에게 매각됐다. 우리가 살 채권이 없다
- **파산선고 및 지위승계 신고**
- **임차인 배당요구 과다** — 최우선변제 총액이 배당을 매입가 아래로 끌어내리는 경우 (**단 3-B 계산 필수**)
- 대항력 있는 선순위 임차인 / 당해세·조세채권 과다

**반려 판정이 나면 STEP 4 이후를 진행하지 않는다.**
계수 조회·수익률 엑셀·매수의향서·PPTX 어느 것도 만들지 않는다. 수익률이 아무리 높아도 무의미하다.

#### 3-A. 이미 산출물이 만들어진 뒤에 발견했다면 ★

문건접수를 늦게 확인했거나, 분석 이후에 채권자변경이 새로 접수된 경우다.

1. 폴더명 앞에 `[폐기] ` 를 붙인다 → `[폐기] NN_짧은주소\`
2. 그 폴더 안에 `★폐기사유.md` 를 만든다
   - 사건번호 · 담보물 주소
   - **반려 사유** (채권자변경 / 승계 / 파산 / 임차인 과다 중 무엇인지)
   - **문건접수 접수일 · 접수자** — 사이트가 마스킹한 형태(`포OOOOOOOO`) 그대로 적는다
   - 원래 산출했던 G15 · 매입가 (있었다면)
   - 판정일
3. **파일은 지우지 않는다.** 수익률 엑셀·의향서·PPTX 전부 그대로 둔다
4. 이력 `status`를 `rejected` 로 바꾸고 `반려사유` 필드를 채운다
5. 번호(`NN`)는 재사용하지 않는다. 다음 합격 물건은 그 다음 번호를 쓴다

> **완전 삭제하지 않는 이유** — 같은 물건이 다음 주에 다시 관심물건으로 잡히면
> 근거가 없어 처음부터 다시 분석하게 된다. 폐기 판단 자체가 자산이다.

> ★ **폴더 이름 변경이 샌드박스에서 막히면 `allow_cowork_file_delete` 를 부르지 않는다**
> (「반드시 지킬 것 8」 참조). `★폐기사유.md` 는 원래 폴더 안에 그대로 만들고,
> 이력 `status`를 `rejected` 로 바꾼 뒤 `폴더명변경실패: true` 를 함께 적는다.
> **이력의 `rejected` 가 정본이다.** 임의로 지우지 않는다.

#### 3-B. 임차인 과다를 이유로 반려·폐기할 때는 계산을 끝내고 한다 ★★

「배당요구 N건」이라는 사실만으로 반려하지 않는다. **아래 4가지를 전부 통과한 계산만 근거가 된다.**

1. **기준일** — 최우선변제 구간은 **최선순위 담보물권 설정일 당시의 시행령**으로 정한다.
   현재 시점 구간을 그대로 쓰지 않는다. 기준일은 등기부 최선순위 근저당 접수일이다.
   정본 절차는 `priority-payment-date-rule` 스킬을 따르고, 금액을 기억으로 쓰지 않는다.
2. **1/2 한도와 안분** — [확정] 주택임대차보호법 시행령 §10② · §10③ (법령ID 004950).
   각 임차인 일정액의 **합이 주택가액의 1/2을 넘으면 1/2에서 잘리고 비율로 안분**된다.
   `N명 × 1인 한도` 를 그대로 빼지 않는다.
   **주택·근생 복합이면 「주택가액」은 주택 부분만**이다. 층별 면적으로 비율을 낸다.
3. **소액임차인 해당 여부** — 배당요구 건수는 소액임차인 수가 아니다.
   보증금이 §11 범위 이하인 임차인만 해당한다. 보증금 미상이면 `[정보부족]` 이지
   「전원 소액임차인」이 아니다. 마스킹된 성(`정OO`)으로 인원을 세지 않는다 — 동일인 중복 접수가 있다.
4. **대항력은 배당 공제가 아니다** — 최선순위 근저당보다 **전입이 앞선** 임차인은 낙찰자가 인수한다.
   배당에서 빼는 것이 아니라 **매입가 자체를 깎아야 하는 사안**이므로 따로 적는다.

**배당요구종기가 미도래면 현재 건수는 최종치가 아니다.** 종기일을 함께 적는다.

**반려·폐기 보고에는 다음을 반드시 적는다.** 하나라도 비면 판정이 아니라 `pending_locked` 다.

```
기준일 <최선순위 근저당 접수일> / 적용 구간 <보증금 한도·최우선변제액> [출처]
배당요구 <N>건 (종기 <날짜> · 미도래면 추가 예상) / 소액 해당 <N>명 / 보증금 미상 <K>명
최우선변제 합계 <금액>원  ← 1/2 한도 적용 전
주택가액 <금액>원 (복합이면 주택 비율 <N>%) · 1/2 <금액>원 · 한도 적용 후 <금액>원
예상낙찰가 <금액>원 − 공제 <금액>원 = 배당가능 <금액>원
채권최고액 <금액>원 / 매입가 <금액>원 → 회수 가능 여부
대항력 인수 예상 <금액>원 (전입이 근저당보다 앞선 임차인)
```

> **실사고 (2026-09-14)** — 12_서울 동대문 휘경동(북부8계 2026-11405)을
> 「배당요구 20건 × 현행 서울 55,000,000원 = 1,100,000,000원」으로 폐기 판정했다.
> 실제로는 배당요구 22건이었고, 최선순위 근저당은 **2020년 01월 14일**이라 기준일이 달랐으며,
> §10②③의 1/2 한도·안분을 적용하지 않았고, 22명 전원이 소액임차인이라는 근거도 없었다.
> 최악 가정으로 다시 계산해도 회수 가능 구간이었고, 감정가 미공시로 확정이 불가해
> 옳은 판정은 폐기가 아니라 `pending_locked` 였다.
> 이미 만들어 둔 매수의향서 1,395,100,000원의 철회가 검토될 뻔했다.

## 1-다. 파싱

표는 `#table1`. **1행 헤더 + 물건당 3행**(본문 / 메모 / 여백) 구조다.

본문 행 셀 순서 — `[체크박스, 사건번호, 물건기본내역, 청구액+alg시세, 개시일+배당종기, 구분]`

| 필드 | 추출 위치 |
|---|---|
| idcode | 행 HTML 의 `pop_wait('<idcode>')` — 39자 |
| 그룹 | 물건기본내역 **첫 대괄호** |
| 경매종류 | 두 번째 대괄호 |
| 물건종류 | 두 번째 대괄호 뒤 첫 토큰 |

### 파싱 값 자체 검산 ★

파싱 직후 아래를 검사하고, 하나라도 걸리면 그 물건을 `failed_parse`로 두고 사건번호를 보고한다.

| 검사 | 조건 | 위반 시 |
|---|---|---|
| 형식 | 청구액·alg시세가 숫자로 파싱되는가 | `failed_parse` |
| 하한 | 청구액 ≥ 10,000,000원 | `failed_parse` |
| 상한 | 청구액 ≤ 10,000,000,000원 | 사람 확인 대상 |
| 상호관계 | alg시세 > 0 이면 `청구액 ≤ alg시세 × 3` | 사람 확인 대상 |
| **alg 결측** | **alg시세 == 0 이면 상호관계 검사가 성립하지 않는다** | **`검산보류` → STEP 3-1** |

> ★★ **alg시세 0을 「검사 통과」로 세지 않는다**
> 예정물건은 감정가 미공시라 alg가 0으로 오는 경우가 흔하다. 종전 규칙은 `alg > 0` 일 때만
> 상호관계를 봤으므로 **0이면 아무 검사도 하지 않고 조용히 통과**했다.

## 1-라. 무결성 가드 ★

## 7.5-C. 거리는 직접 계산한다 ★★

**카카오맵은 거리순으로 정렬해 주지 않는다.** 실측: 안중읍 검색에 13.2km 서정리역이 1순위였다.

1. 각 역의 **주소**를 `geocode_address`로 좌표 변환
2. 물건 좌표와 **직선거리(haversine)** 계산
3. 가까운 순 정렬 후 **상위 3개만** 남긴다

```python
from math import radians, sin, cos, asin, sqrt
def km(p, q):
    (x1, y1), (x2, y2) = p, q          # (경도, 위도)
    x1, y1, x2, y2 = map(radians, [x1, y1, x2, y2])
    return 2*6371*asin(sqrt(sin((y2-y1)/2)**2 + cos(y1)*cos(y2)*sin((x2-x1)/2)**2))
```
