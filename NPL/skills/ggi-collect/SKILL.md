## STEP 1 — 진입 및 로그인 확인

좌표 클릭을 쓰지 말고 URL로 직접 간다.

```
navigate → https://www.ggi.co.kr/search/total_search.asp
```

### ★★ 최상위 document 를 본다. iframe 이 아니다

```javascript
const t = document.body.textContent || '';
const links = [...document.querySelectorAll('a')].map(a => (a.textContent||'').trim());
({ 로그인: /로그아웃/.test(t),
   상단링크: links.filter(Boolean).slice(0, 10) })
```

**전에는 `document.querySelector('iframe')?.contentDocument || document` 였다. 그것은 틀렸다.**
페이지에 iframe 이 하나라도 있으면 그 안을 들여다보는데, 로그인 표시는 **최상위에 있다.**
정상 로그인 상태에서도 `false` 가 나온다 — 스킬대로 따르면 **매주 여기서 즉시 중단된다.**

(2026-08-14 실측: 로그인돼 있는데 검사가 `false`. 최상위 상단 링크에 `로그아웃` 과
계정 ID 가 멀쩡히 있었다. iframe 하나가 있었고 그 안에는 없었을 뿐이다.)

`false` 가 나오면 상단 링크 목록을 한 번 더 확인하고, **거기에도 `로그아웃` 이 없을 때만**
중단하고 재로그인을 요청한다. (요청은 보고에 적는 것으로 끝낸다. 응답을 기다리지 않는다.)

## STEP 2 — 검색 모드

`total_search.asp`로 직접 가면 폼이 **최상위 document**에 있다 (iframe 안이 아니다).

### ★★ resultchk — 가장 중요한 선택

| id | value | 라벨 | 성격 |
|---|---|---|---|
| `resultchk1` | `N` | 경매종합검색 | **최종 경매 결과** 기준 |
| `resultchk2` | `Y` | 입찰당일 결과검색 | **그 날짜 당일 결과** |

**낙찰률이 필요하면 반드시 `Y`.** `N`은 유찰됐다가 나중에 매각된 물건을 "매각"으로만 잡아
**유찰 이력이 통째로 사라진다.**

라디오만 바꾸면 안 되고 핸들러도 호출: `chk_ipchalresult()`

| 모드 | 날짜 필드 | 단위 |
|---|---|---|
| `Y` | `resResultdate` (`YYYY-MM-DD`) | **하루씩** |
| `N` | `resYear1`~`resDay2` + `SDay` | 기간 범위 |

`N` 모드에서만: `SDay` 라디오를 `id=SDay`(value `1`, 기간설정)로 바꾸고
`ChangSelect('1'); ChangSelect2('1');` 호출. 기본값 `2`(오늘이후)면 오늘 것만 나온다.

### 공통 필드

| 필드 | 값 |
|---|---|
| `resSiDo` | `09`=서울 `02`=경기 `00`=전국 |
| `resSiGuGun` | **비워둔다** → 시도 전체 |
| `resAuctionResult2` | **`Y` 모드의 결과 필터.** 아래 경고를 먼저 읽는다 |
| `resAuctionResult` | `N` 모드용. **`Y` 모드에서는 아무 효과가 없다** |
| `pgesize` | `100` |
| `nowPge` | 페이지 번호 |

### ★★ `Y` 모드의 결과 필터는 `resAuctionResult2` 다

`resultchk2=Y` 로 조회하면서 `resAuctionResult` 에 값을 넣으면 **조용히 무시된다.**
필드가 존재하고 값도 들어가지만 검색에 반영되지 않는다. 오류도 나지 않는다.

(2026-08-14 실측: 경기 08-11 을 전체·매각·유찰로 나눠 조회했더니 **셋 다 800건**으로 같았다.
`resAuctionResult2` 로 바꾸자 유찰이 565건으로 제대로 갈렸다.)

**`03,06` 같은 조합값은 `resAuctionResult2` 에서도 무시되어 전체로 떨어진다.**
같은 조회에서 유찰(`02`)은 565건인데 매각(`03,06`)은 800건(=전체)이 나왔다.
단일값(`02`, `07`, `01`)만 신뢰할 수 있다.

**기본 방침 — 결과 필터를 쓰지 않는다.**
전체(`''`)로 받아 파서가 뽑은 `상태` 로 나눈다. 낙찰률에는 어차피 유찰과 매각이 둘 다 필요하다.
필터를 쓸 때는 반드시 건수를 교차 대조하고, 합이 전체와 맞는지 확인한다.

### ★ 당일(오늘)은 수집 창에서 제외한다

당일은 **유찰 결과가 아직 안 올라온다.** 매각 건만 먼저 반영되어 낙찰률이 터무니없이 높게
나온다. (2026-08-07 실측: 서울 366건 중 249건이 진행·신규 상태, 확정분만으로 낙찰률 83%)

수집 창은 **어제까지**로 잡는다.

## STEP 3 — 수집 (숨은 iframe + 재시도)

최상위에서 `frmSearch.submit()`을 하면 페이지가 이동하며 함수가 사라진다.
**숨은 iframe 안에서 제출**하면 최상위 컨텍스트가 살아남는다.

```javascript
let fr = document.getElementById('__gg');
if (!fr) { fr = document.createElement('iframe'); fr.id='__gg';
  fr.style.cssText='position:fixed;left:-9999px;width:1200px;height:800px';
  document.body.appendChild(fr); }
await new Promise(r => { fr.onload = r; fr.src='https://www.ggi.co.kr/search/total_search.asp'; });
await new Promise(r => setTimeout(r, 1500));

window.__setDay = function (page, sido, ymd, res) {
  const d = document.getElementById('__gg').contentDocument;
  const w = document.getElementById('__gg').contentWindow;
  d.getElementById('resultchk2').checked = true;
  try { w.chk_ipchalresult(); } catch(e) {}
  const S=(n,v)=>{const e=d.querySelector(`[name=${n}]`); if(e) e.value=v;};
  S('resResultdate', ymd);
  S('resSiDo', sido); S('resSiGuGun','');
  S('resAuctionResult','');            // N 모드 잔재를 비운다
  S('resAuctionResult2', res || '');   // ★ Y 모드의 진짜 필터. 기본은 전체
  S('pgesize','100'); S('nowPge',String(page));
  return d.frmSearch;

```

`__setDay` 가 매 호출마다 `resAuctionResult2` 를 초기화하는 것이 중요하다.
비워 두면 직전 조회의 필터가 남아 다음 날짜를 오염시킨다.

### ★ 재시도 필수 — 간헐적 0건 응답이 있다

서버가 이유 없이 빈 결과를 돌려준다.
(2026-08-07 실측: 경기 08-05가 1차 조회 0건, 재시도에서 428건)

**재시도 없이 돌리면 하루치가 조용히 통째로 빠진다.**

```javascript
window.__page = async function (page, sido, ymd, tries) {
  const fr = document.getElementById('__gg');
  for (let a = 0; a < (tries || 3); a++) {
    const form = window.__setDay(page, sido, ymd);
    const done = new Promise(r => { fr.onload = r; });
    form.submit(); await done;
    await new Promise(r => setTimeout(r, 900 + a * 800));
    const rows = window.__parse(fr.contentDocument);
    const tot  = window.__total(fr.contentDocument);
    if (rows.length > 0 || tot === 0) return { rows, tot };
  }
  return { rows: [], tot: -1 };      // 3회 실패 — 호출부에서 경고 처리
};

window.__total = function (doc) {
  const b = doc && doc.body; if (!b) return null;      // iframe 이동 중이면 null
  const m = (b.textContent||'').match(/총\s*([\d,]+)\s*건/);
  return m ? +m[1].replace(/,/g,'') : null;
};
```

`tot === -1`이면 그 날짜·지역을 **실패로 기록하고 보고에 명시**한다.

### ★★ 총건수가 100의 배수면 마지막 빈 페이지를 실패로 오인한다

`pgesize=100` 이므로 총 800건이면 8페이지에서 정확히 끝난다. 그런데 호출부가
"이번 페이지가 100건 꽉 찼으니 다음이 있다"고 판단해 9페이지를 요청하면 0건이 온다.
그때 `tot` 은 0이 아니므로 위 재시도 로직이 3회를 돌린 뒤 `-1`(실패)을 돌려준다.

**데이터는 온전한데 매주 허위 실패가 보고된다.**
(2026-08-14 실측: 경기 08-11, 800건 전량 수집했는데 실패로 기록됐다)

수집 루프는 페이지 수가 아니라 **누적 건수**로 끝낸다.

```javascript
let 누적 = 0, tot = null, 실패 = false;
for (let p = 1; p <= 12; p++) {
  const r = await window.__page(p, sido, ymd, 3);
  if (r.tot === -1) { 실패 = true; break; }
  if (p === 1) tot = r.tot;
  if (!r.rows.length) break;
  누적 += r.rows.length;
  if (누적 >= tot || r.rows.length < 100) break;   // ★ 누적으로 판정한다
}
```

### ★ 총 건수 대조

서버의 `총 N 건`과 실제 수집 건수를 반드시 대조한다. 차이가 나면 마지막 페이지를 다시 받는다.
(2026-08-07 실측: 서울 08-03이 "총 101건"인데 100건만 수집됨)

**`총 N 건` 은 표시 상한이 아니다.** 800 처럼 딱 떨어지는 값이 나와도 절단이 아니다.

(2026-08-14 검증: 경기 08-11 "총 800건"을 캡으로 의심해 시군구 32개로 쪼개 전량 재수집했더니
합계 800건, 직진 수집분과 사건 집합이 **완전히 일치**했다 — 차집합 0.
캡으로 오판한 원인은 위 `resAuctionResult` 필드명 오류였다.
매각·유찰 필터가 셋 다 800을 돌려주는 것을 보고 "상한"이라 결론지었는데, 필터가 무시된 것이었다.
**딱 떨어지는 숫자를 캡이라고 부르기 전에 쪼개서 합을 맞춰 본다.**)

시군구로 쪼개야 할 때 `resSiGuGun` 은 코드가 아니라 **이름 문자열**(`"수원시 영통구"`)이다.
상위 시(`"수원시"`)와 하위 구(`"수원시 영통구"`)가 옵션에 함께 있으므로,
전량 수집에는 **공백이 없는 상위 항목만** 쓴다. 둘을 섞으면 이중 계상된다.
옵션 목록에 있는 `99` 는 시군구가 아니다 — 필터가 무시되어 전체가 나온다. 제외한다.

실측 사례가 있다. 행 수가 아니라 **데이터 행의 생김새**로 표를 고른다.

```javascript
      응찰: 매각 ? num((c4.find(x=>/응찰/.test(x))||'').replace(/응찰/,'')) : 0,
      최저율:pct[0]||0,
      매각율: 매각 ? (pct[1]||0) : 0,                        // ★ 매각만 두 번째 %
      건물면적:num((ar.match(/건물\s*([\d,]+)㎡/)||[])[1]),
      토지면적:num((ar.match(/토지\s*([\d,]+)㎡/)||[])[1]),조회수:num(c6[0]||0)});
  }
  return out;
};
```

**상태 판정이 핵심이다.** 매각 건만 `(최저가율%) (매각가율%)` 두 개가 나온다.
상태를 보지 않고 `money[2]`를 매각가로 쓰면 유찰 건에 엉뚱한 값이 들어간다.

`innerText`는 레이아웃 없는 문서에서 빈 문자열을 돌려주므로 반드시 `textContent`를 쓴다.

**파서를 손댔으면 `소재지`·`토지면적` 이 살아 있는지 CSV 로 확인하고 넘어간다.**
PK 가 (법원, 사건번호, 매각기일) + `INSERT OR IGNORE` 라서, 빈 값으로 한 번 적재되면
나중에 제대로 받아도 **영구히 덮이지 않는다.** (2026-08-14: 두 칸을 빠뜨린 채 CSV 를
만들다가 저장 직전에 발견해 전량 재수집했다)

### 실패 감지

| 상황 | 판정 |
|---|---|
| 상태에 **`유찰`이 하나도 없음** | `resultchk=Y`가 안 걸린 것. 즉시 중단 |
| 수집 건수 ≠ 서버의 `총 N 건` | 마지막 페이지 누락. 재수집 |
| 3회 재시도 후에도 0건 | 그 날짜·지역 실패로 **보고에 명시** |
| 서울+경기 10영업일 합계 1,000건 미만 | 로그인 만료 의심 |
| 매각 건 중 응찰자수 결측 10% 초과 | 파서 손상 의심 |
| **소재지 결측 0% 초과** | 파서에서 칸이 빠졌다. 적재 전에 고친다 |

정상 규모(2026-08-07 실측, 평일 10일): 서울 2,633건 / 경기 2,722건. 경기 평일 하루 약 336건.

## STEP 5 — CSV 내려받기

### ★★ Chrome이 반복 다운로드를 차단한다

같은 탭에서 두 번째 파일을 내려받으려 하면 Chrome이 막는다.

대응 순서:

1. 첫 파일 저장 → **데이터를 `sessionStorage`에 옮겨 담는다**
2. 페이지를 새로고침한다 (`location.reload()`) — 다운로드 차단 상태가 풀린다
3. `sessionStorage`에서 꺼내 두 번째 파일을 저장한다

**저장 후 반드시 파일이 전부 생겼는지 확인한다.**
지역 2개면 CSV도 2개여야 한다. 하나라도 없으면 **보고 첫머리에 경고**하고,
누락된 지역을 다시 저장한다. 누락된 채로 "완료"라고 보고하지 않는다.

확인은 눈으로 하지 말고 **DuckDB 로 실물을 읽어** 행수·기간·상태 분포를 대조한다.

```sql
SELECT 시도, count(*), min(매각기일), max(매각기일),
       count(*) FILTER (상태='매각'), count(*) FILTER (소재지 IS NULL OR 소재지='')
FROM read_csv('%USERPROFILE%\Downloads\ggi_*.csv', union_by_name=true, all_varchar=true)
GROUP BY 1;
```

- 날짜는 `YYYY-MM-DD` (`2026.07.01` 형태는 도구 보안 필터에 가려진다)
- UTF-8 BOM(`﻿`)을 앞에 붙인다
- 파일명 `ggi_{지역}_{시작}_{종료}.csv`

DuckDB로 **READ_ONLY** 붙인다.

### 집계 4원칙

**① 일괄매각을 정제한다.** 사건번호의 `[숫자]`를 떼어 그룹핑하고 **중앙값**을 대표값으로.
(실측: 4,426 사건 중 302 사건이 분할, 최대 41분할)

**★ 부분 유찰 사건 — 매각가율·응찰자수 중앙값은 팔린 물건만으로 낸다.**
한 사건에서 일부만 팔리고 나머지가 유찰되면, 파서가 유찰 물건에 넣은 **매각가율 `0`이
중앙값에 섞여 그 사건의 낙찰가율이 통째로 내려간다.**
그룹 중앙값을 구할 때 `상태 = '매각'` 인 물건만 남기고 계산한다.
유찰 물건은 낙찰률 분모(원칙 ③)에만 쓰고 가격·응찰 중앙값에서는 뺀다.
(2026-08-09 실측: 매각·유찰 혼재 사건 50건이 평균 **31.4%p** 눌려 있었다)

**★ 매각기일이 `YYYY-MM-DD` 형식이 아닌 행은 표본에서 제외한다.**
과거 컬럼 밀림 사고의 잔재가 남아 있어, 그대로 두면 날짜 구간 필터가 어긋나 표본이 뒤틀린다.

**② 회차를 섞지 않는다.** 유찰 6회(13%)와 신건(110%)을 함께 평균 내면 의미가 없다.

**③ 낙찰률 분모에서 변경·취하·기각을 뺀다.** `낙찰률 = 매각 ÷ (매각 + 유찰)`.

**④ 낙찰률은 '유찰이 수집된 날짜'로만 계산하고 당일은 뺀다.**
매각만 수집한 기간이 섞이면 분모에 유찰이 없어 부풀려진다(실측: 41% → 72%).

### ★★ SQL 로 정제를 다시 짜지 않는다

집계·진단·계수 산출은 **모두 `load_ggi_csv.정제(con)` 를 import 해서 호출한다.**
2026-08-14에 SQL로 재구현했다가 다섯 군데가 어긋났다 — 그룹 키, 회차 역산 허용범위,
저감 사다리 판정, 트림 하한, 동산 제외. **적합과 진단이 다른 정제를 쓰면 결과가 무의미하다.**

`정제()` 반환: `(유찰회차, 응찰자수, 매각가율, 조회수, 상태, 용도군, 매각기일, 저감률)`.
**법원은 반환되지 않는다** — 법원 축 분석이 필요하면 별도 경로를 찾아야 한다.

### ★★ 유찰회차 역산 — 저감률이 법원마다 다르다

최저가율로 유찰회차를 역산할 때 **30% 저감 사다리 하나로 밀면 안 된다.**
저감률은 법원마다 다르고, **전체 사건의 36.7%가 20% 저감 법원 소속이다.**

| 저감률 | 사다리 (최저가율 → 유찰회차) | 해당 법원 |
|---|---|---|
| **30%** | `{100:0, 70:1, 49:2, 34:3, 24:4, 17:5, 12:6, 8:7}` | 경기 대부분 — 부천·고양·의정부·평택·수원·성남·남양주·안산·여주 |
| **20%** | `{100:0, 80:1, 64:2, 51:3, 41:4, 33:5, 26:6}` | **서울중앙·서울남부·서울동부·서울서부·서울북부 + 수원지법 안양지원** |

(±3%p 허용)

30% 사다리 하나로 밀면 두 가지가 벌어진다.

1. **버려진다** — `80%` · `64%` · `41%`는 30% 사다리 어디에도 안 걸려 통째로 탈락한다
2. **오분류된다** — `51↔49`, `33↔34`, `26↔24`는 ±3 허용범위 안에서 충돌해 **잘못된 회차로
   들어간다** (2026-08-09 실측: 유찰 2회로 잡힌 표본 708건 중 **89건이 실제로는
   20% 저감 3회**였다)

**버리는 것보다 오분류가 나쁘다.** 표본이 줄어드는 것은 신뢰구간이 넓어질 뿐이지만,
오분류는 계수 자체를 틀린 방향으로 끌고 간다.

**법원 목록을 코드에 하드코딩하지 말 것.**
`load_ggi_csv.py`의 `저감사다리(con)` 함수가 법원별 최저가율 분포를 세어 저감률을
자동 판정한다. 표본 10건 미만인 법원은 **30%(다수파)로 폴백**한다.
법원 신설·관할 변경 때 코드를 고치지 않아도 되도록 유지한다.

**집계는 반드시 저감률별로 분리한다.**
30% 1회는 최저가 70%, 20% 1회는 80%다. 같은 표에 섞으면 회귀가 **이중 봉우리**가 되어
회차별 계수가 무의미해진다. `GROUP BY 저감률, 유찰회차` 로 낸다.

**★ `auction-bid-price` 【A】의 "n회"는 유찰 n회다.** 신건이 아니다.

### ★★ 이상치 트림 규약

**매각가율이 `[해당 회차 최저가율, 200]` 밖이면 표본에서 제외한다.**

| 경계 | 값 | 근거 |
|---|---|---|
| 하한 | **그 회차의 최저가율** | 낙찰가는 최저가 미만일 수 없다. 그보다 낮으면 데이터 오류 |
| 상한 | **200%** | 감정가 2배 초과 낙찰은 입력·파싱 오류로 본다 |

하한은 저감률·회차에 따라 달라진다(30% 2회 = 49%, 20% 2회 = 64%). 고정값을 쓰지 말고
그 행의 회차·저감률에서 계산한 최저가율을 쓴다.

(2026-08-09 실측: **매각가율 664% 한 건**이 20% 저감 2회 회귀의 상관계수를
**0.440 → 0.071**로 무너뜨리고 있었다. 공매 쪽에는 트림 규약이 있었는데 경매에는 없었다.)

### 탐색 결과를 계수로 쓰지 않는다

여기서 나온 수치는 전부 `[검증필요]`다. 정식 계수 반영은 **화요일 10:09**
`court-auction-weekly-collect`의 STEP 5가 `coefficient-auto-update` 4개 게이트를 거쳐
`save_skill`로 수행한다. 표본 30건 미만 구간은 반영하지 않는다.

수집 직후 `coefficient-self-diagnosis` 로 **직전 계수의 홀드아웃 잔차**를 함께 낸다.
새로 들어온 건이 87건(실측 sd 기준 재계산)을 넘으면 진단이 성립한다.
