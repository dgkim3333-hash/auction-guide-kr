## STEP 2 — DB 3종 상태

```sql
INSTALL sqlite; LOAD sqlite;
ATTACH '<경로>/court_sale_results.sqlite' AS 경매 (TYPE sqlite, READ_ONLY);
ATTACH '<경로>/onbid_bidresult.sqlite'    AS 공매 (TYPE sqlite, READ_ONLY);
ATTACH '<경로>/ggi_sale_result.sqlite'    AS ggi  (TYPE sqlite, READ_ONLY);
```

**반드시 READ_ONLY 로 붙인다.** 삭제 권한이 없는 상태에서 쓰면 SQLite 가 커밋 후
`-journal` 을 지우지 못해 `disk I/O error` 로 나타나고 파일이 손상된다
(2026-08-07 원인 특정. 마운트의 한계가 아니라 삭제 권한 문제다).

| DB | 테이블 | 최신 날짜 컬럼 | 경고 기준 |
|---|---|---|---|
| `court_sale_results.sqlite` | `sale_result` | `collected_at` | **9일 초과** |
| `onbid_bidresult.sqlite` | `bidresult` | `cltrOpbdDt` | **40일 초과** |
| `ggi_sale_result.sqlite` | `ggi_sale` | `수집일` | **9일 초과** |

함께 볼 것:

- **행수** — 직전 점검보다 줄었으면 사고다. 단, 로그에 의도적 정리 기록이 있으면 예외
  (`ggi_sale` 은 적재마다 `init_db()` 가 미확정 행을 지운다. 2026-08-07 실측 249/6,885 = 3.6%)
- **`PRAGMA integrity_check`** — `ok` 가 아니면 즉시 경고
- **`*-journal` / `*-wal` / `*-shm` 잔존** — 다음 접근 때 DB가 0바이트로 잘릴 수 있다
  (2026-08-04 실제 발생)

★ **DuckDB 에서 integrity_check 를 부르는 법.** 인자는 **ATTACH 별칭**이지 파일 경로가 아니다.
경로를 넣으면 `Failed to find attached database` 가 난다 (2026-08-27 실측).

```sql
SELECT 'ggi' AS db, * FROM sqlite_query('ggi','PRAGMA integrity_check');
```

**같은 세션에서 같은 별칭으로 두 번 ATTACH 하면 `already exists` 로 실패한다.**
한 번 붙였으면 이후 쿼리는 ATTACH 없이 별칭만 쓴다.

## STEP 3 — 계수이력이 늘고 있는가 ★ 가장 중요

**이 항목이 이 스킬을 만든 이유다.**

| 파일 | 구조 | 식별 필드 | 기대 증가 |
|---|---|---|---|
| `경매_매각결과DB/계수이력.json` | `{"이력": [...]}` 객체 | `주차` | **주 1건** |
| `공매_입찰결과DB/공매_계수이력.json` | 최상위 배열 | `회차` | **월 1건** (재산유형별) |

**두 파일은 경로·구조·필드명이 전부 다르다. 섞지 말 것.**

확인할 것:

- 마지막 항목의 `수집일`이 최근인가
- 항목 수가 지난 점검 대비 늘었는가

**이력이 안 늘면 계수는 영원히 안 바뀐다.** 수집만 하고 반영이 안 되는 상태다.

다만 **월 1일 회차가 하나라도 빠지면 그만큼 더 밀리므로**, 매월 첫 점검에서

★ **주간로그와 이력 파일이 어긋날 수 있다.** 주간로그는 실행 시점 스냅샷이고,

**정본은 `계수이력.json` 이다.** 로그만 읽고 "반영 안 됨"으로 판정하지 않는다

- 0바이트가 없는가
- **크기가 아니라 행수로 본다.** SQLite 자유 페이지 재사용 때문에 행이 늘어도 크기가 그대로일 수 있다
  (실측: ggi 백업이 8/09~8/13 내내 2,613,248 바이트로 동일한데 내용은 257행 늘었다)

`backup_db.py` 는 온라인 백업 API + 원본·사본 양쪽 `integrity_check` + 행 0건 거부를
이미 수행한다. **`rc=0` 이면 무결성 검사를 통과한 것이 맞다.**
2026-08-13 에 직전 백업 대비 **10% 초과 감소 시 회전 건너뜀** 가드를 추가했다.
로그에 `행수 급감` 이 보이면 회전이 멈춘 것이므로 보관본이 KEEP(8)을 넘어 쌓인다 — 정상 동작이다.

★ `00_시장데이터/_백업상태_일일.json` · `_백업상태_주간.json` 은 Windows 작업 스케줄러가
백업을 마칠 때마다 새로 쓴다. **예약 세션은 D 드라이브에 접근하지 못하므로**
(예약 세션의 셸은 Linux 샌드박스이며 마운트된 폴더만 보인다 — 2026-08-18 실측)
이 두 파일이 백업 결과를 확인할 수 있는 유일한 창이다. 원본을 찾으러 D 드라이브로 가지 말 것.
**두 파일의 `DB[].integrity` 가 전부 `ok` 인지, `오류` 배열이 비어 있는지도 여기서 본다.**

## STEP 7 — 자가진단

```
python <작업폴더>/run_all_tests.py
```

**절대 숫자를 이 문서에 판정 기준으로 박지 않는다.**
기준선은 `run_all_tests.py` 안의 `EXPECT` 값이고, 그 스크립트가 파일별 미달을
이미 실패로 잡는다. 이 문서에 숫자를 박으면 케이스가 늘 때마다 낡고,
낡은 줄 모른 채 지나간다 — **이 문서가 124로 남아 있는 동안 실제는 209였고
(2026-08-13 발견), 화요일 프롬프트가 202로 남아 있는 동안 실제는 261이었다
(2026-08-27 발견, 3주 묵음).**

점검할 것:

- 종료코드가 0인가
- 파일별 출력에 `케이스 N개 < 기대 M개` 가 있는가
- 총 케이스 수가 **직전 점검 기록보다 줄지 않았는가**

참고값 — 2026-08-27 기준 **261개**
(적재 지지옥션 58 / 수집 법원경매 34 / 수집 온비드공매 57 / 계수 산출 46 / 백업 3개 DB 33 / 진단 계수자가 33).
케이스를 추가하면 `run_all_tests.py` 의 EXPECT 를 함께 올린다.
**이 숫자는 직전 비교용 참고값이지 판정 기준이 아니다.** 보고에는 그날 실측치를 쓴다.

## STEP 8 — 미결현황 적체 ★

`00_시장데이터/미결현황.md` 를 **반드시 읽는다.**

| 볼 것 | 처리 |
|---|---|
| `등록일` 이 **3주 넘은 미해결 항목** | 보고 **첫머리에 ★** 로 올린다. 묵을수록 잊힌다 |
| `다음 확인` 시점이 지난 항목 | 이번 회차에 확인 가능하면 확인하고 결과를 적는다 |
| 이번 점검에서 새로 찾은 이상 | 보고에 쓰는 것으로 끝내지 말고 **미해결 표에 추가**한다 |
| 해결된 항목 | `해결` 표로 옮기고 **해결일과 방법**을 적는다. 행을 지우지 않는다 |

**왜 이 단계가 생겼나** — 「대표 확인 필요」를 주간수집로그와 점검 보고에만 적으면
다음 회차가 그 파일을 읽지 않아 그대로 묻힌다. 매주 새로 발견해서 매주 다시 적을 뿐,
고치는 단계가 어느 프롬프트에도 없었다.
**「자가진단 202개가 낡음」 지적이 2026-08-18·08-25 두 회차 로그에 적혔는데도
3주를 묵은 것**이 그 증거다 (2026-08-27 원인규명).

**보고에 쓴 것과 미결현황에 남긴 것이 다르면 미결현황이 정본이다.**

## 보고 형식

**결론을 먼저 쓴다.** 이상이 없으면 한 줄로 끝낸다.

```
✅ 파이프라인 정상 — 이상 없음 (점검 2026-08-27)
   최근 수집: ggi 8/25 · 경매 8/25 · 공매 8/04
   계수이력: 경매 9주차 / 공매 1회차
   자가진단: 261개 통과
   미결현황: 잔여 5건 (3주 초과 0건)
```

이상이 있으면:

```
⚠ 파이프라인 이상 2건

★ 계수이력이 2주째 안 늘어남 (마지막 주차 6, 2026-08-07)
    → 화요일 작업이 STEP 3 을 실행하지 못하고 있다.
      다음 화요일 보고에서 "주차 N 기록" 문구를 확인할 것.
      2026-08-04 에 같은 일이 있었고 5일 뒤에야 발견했다.

★ ggi_sale 최신 수집일이 11일 전
    → 월요일 수집 또는 적재가 밀렸다.
      _load_log.txt 마지막 START 시각과 대기 CSV 를 함께 확인.

정상: DB 무결성 3종 ok / 백업 4일 이내 / 자가진단 261개 통과 / 미결현황 잔여 5건
```

### 규칙

- **이상이 없어도 핵심 수치는 남긴다.** "정상"만 쓰면 다음 점검 때 비교할 기준이 없다
- 금액은 원 단위 풀 콤마. 행수는 콤마 구분
- 추측하지 않는다. 확인할 수 없는 항목은 **"확인 불가 — 대표 확인 필요"** 로 명시
- **고치지 않는다.** 이 스킬은 진단 전용이다. 처방은 해당 스킬(`coefficient-auto-update` 등)에 맡긴다.
  **단 미결현황 기록(STEP 8)은 예외다** — 기록하지 않으면 지적이 사라진다
- **"조치 필요 없음"과 "이상 없음"을 구분한다.** 확인이 필요한 항목을 ★로 적어놓고
  머리말에 "이상 없음"이라 쓰면 대표가 본문을 안 읽는다
- **「대표 확인 필요」로 보고한 것은 빠짐없이 `미결현황.md` 에도 들어가 있어야 한다**

| hot journal 잔존 | `*-journal` 파일 존재 | STEP 2 |

| 테스트가 조용히 사라짐 | 케이스 수가 EXPECT 미달 | STEP 7 |
