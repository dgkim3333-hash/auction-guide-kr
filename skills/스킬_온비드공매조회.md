# 온비드 공매 조회 스킬

## 목적

공공데이터포털(data.go.kr)의 온비드 API를 MCP 도구로 호출할 때 **첫 호출에 성공**하고 **물건을 빠뜨리지 않고** 데이터를 얻기 위한 표준 규칙이다.

> 이 스킬의 결과는 **검토 후보 목록일 뿐 입찰 권유가 아니다.**
> AI 분석은 검토 출발점입니다. 실제 입찰 전 공매재산명세서 원문과 전문가 확인이 필요합니다.

### 표기 규칙

- 근거 라벨은 세 가지만 쓴다: **[출처확인]**(API 응답·온비드 화면으로 확인) / **[미확인]**(확인 못 함) / **[추정]**(계산·추론).
- 원화 금액은 **원 단위 풀 콤마**로 쓴다. 예: `1,234,560,000원`. 금액을 줄여 쓰는 한글 단위는 쓰지 않는다.
- 물건관리번호 같은 식별번호에는 콤마를 넣지 않는다.

---

## 준비 — 이것이 없으면 시작하지 않는다

1. **공공데이터포털 인증키**: data.go.kr 회원가입 후, 온비드 관련 서비스(온비드 부동산 물건 목록, 공고 목록, 입찰결과 등)마다 **「활용신청」** 이 승인돼 있어야 한다. 서비스마다 따로 신청한다.
2. **온비드 도구를 제공하는 MCP 서버 1개**: 아래 도구 이름(`onbid_realestate_list`, `onbid_notice_list`, `get_public_auction_items` 등)을 노출하는 공공데이터포털용 MCP 서버가 Claude에 연결돼 있어야 한다. 도구 이름 앞의 접두어(예: `mcp__서버이름__`)는 연결한 서버에 따라 다르다.
3. **도구가 연결돼 있지 않으면**: "온비드 조회 도구가 연결돼 있지 않습니다"라고 알리고 **멈춘다.** 웹 검색이나 기억으로 물건 목록·금액을 지어내지 않는다.

---

## 규칙 0: 세 API의 역할이 다르다 — 목적에 맞는 것을 고른다

가장 자주, 가장 비싸게 틀리는 지점이다. [출처확인]

| 도구 | 성격 | 개찰 전 물건 | 공고일 | 감정가·최저가 | 지역 필드 |
|---|---|---|---|---|---|
| `get_public_auction_items` | **입찰결과** (개찰 끝난 회차) | **없음** | 없음 | 있음 | 주소 문자열(마스킹 많음) |
| `onbid_realestate_list` | **진행중·입찰예정 물건** | **있음** | 없음 | 있음 | **구조화 필드** |
| `onbid_notice_list` | **공고 목록** | 있음(공고 단위) | **있음** | 없음 | 없음 |

### 목적별 선택

- **낙찰가·낙찰률·응찰자수 등 결과 통계** → `get_public_auction_items`
- **지금 입찰할 수 있는 물건** → `onbid_realestate_list`
- **최근 새로 올라온 공고** → `onbid_notice_list` 로 공고일을 잡고 `onbid_realestate_list` 와 공고번호로 연결

### 예시 — 결과 API의 한계 (가상의 물건)

온비드 화면에는 물건 `2026-00000-001` 의 회차 1~10이 공개돼 있다고 하자.

```
회차3  입찰 09-07  개찰 09-08  최저 1,000,000,000원
회차4  입찰 09-10  개찰 09-11  최저   900,000,000원   ← 온비드 화면에는 있다
회차5  입찰 09-14  개찰 09-15  최저   810,000,000원   ← 온비드 화면에는 있다
```

`get_public_auction_items` 에는 **개찰이 끝난 회차 3까지만** 나온다. 회차1 개찰 전이라면 그 물건은 응답에 아예 없다.
→ 결과 API만 보면 "한 번도 관측되지 않은 채 팔린 물건"이 생긴다. 입찰 가능 물건은 반드시 `onbid_realestate_list` 로 본다.

## 규칙 0-1: `onbid_realestate_list` — `pvct_trgt_yn="N"` 이 필수다

이 파라미터를 빼면 `NO_MANDATORY_REQUEST_PARAMETERS_ERROR`(코드 11)가 난다. [출처확인]
**이 오류를 보고 "고장 난 도구"로 판정하지 않는다.** 파라미터만 넣으면 정상 동작하며, 입찰 가능 물건을 물건 단위로 받는 사실상 유일한 경로다.

```python
onbid_realestate_list(
    prpt_div_cd="0003,0005,0007",
    pvct_trgt_yn="N",            # ★필수. 빠뜨리면 코드 11
    lctn_sdnm="서울특별시",       # 시도만 넣는다
    num_of_rows=1000, page_no=1) # 끝까지 페이징
```

참고 규모: 원 작성 시점에 서울특별시 약 6,000건, 경기도 약 16,000건이 나왔다. 시점마다 다르다. [출처확인]

### 이 도구가 좋은 이유

- **`lctnSdnm` · `lctnSggnm` · `lctnEmdNm` 이 구조화 필드로 온다.** 주소 문자열을 파싱할 필요가 없다. `lctn_sggnm` 은 넣지 말고 시도 단위로 받은 뒤 응답 필드로 거르는 편이 안전하다.
  - 경기도는 `lctnSggnm` 이 `"수원시 영통구"` 처럼 구까지 붙어 온다. 시 이름으로 **시작**하면 통과시킨다.
- **`pbctStatNm` 이 `입찰준비중`·`입찰진행중`** 으로 온다.
- **`usbdNft` = 유찰 횟수**가 그대로 있다. 환산할 필요가 없다.
- `cltrBidBgngDt` / `cltrBidEndDt` = 입찰기간. 같은 `cltrMngNo` 의 **향후 회차를 미리 반환**하므로, 다음 회차 최저가는 추정하지 말고 이 실제 값을 인용한다.
- 압류재산이 주소 마스킹 없이 나온다.

### 주의

- `apslPrcCtrsLowstBidRto` · `feeRate` 가 **거의 전부 null** 이다. 최저가율은 `lowstBidPrcIndctCont ÷ apslEvlAmt × 100` 으로 직접 계산하고 계산식을 함께 적는다.
- `apslEvlAmt`(감정가)가 **null 인 행**이 있다(신탁공매에 많다). 감정가 조건으로 거를 때 이런 행을 조용히 통과시키거나 버리지 말고 따로 표시한다.
- 일정 미정 행은 `cltrBidEndDt` 가 `"299901021600"` 처럼 **2999년·9999년**으로 온다. 날짜로 변환하지 말고 `일정 미정` 으로 쓴다.
- 감정가 상·하한 파라미터가 없다. 받은 뒤 직접 거른다.

## 규칙 0-2: 신규 물건은 「공고일」 기준으로 판정한다

개찰일 기준으로 "새 물건"을 잡으면 **압류재산이 통째로 사라진다.** [출처확인]

### 왜 그런가

캠코 압류재산은 **2주에 한 번 몰아서 개찰**한다. 그 사이 기간에는 압류재산 개찰이 0건이다.

```
(예시) 08-27 개찰   09-03 개찰   ← 과거
                                  09-08 · 09-09 → 압류재산 개찰 0건
09-17 개찰   10-01 개찰   10-08 개찰   ← 앞으로
```

원 작성자 실측에서 개찰일 기준으로 뽑은 신규 물건은 전부 기타일반재산이었고 압류재산은 0건이었다. 게다가 그 물건들은 개찰이 코앞이라 **입찰이 이미 마감된 상태**였다(입찰은 개찰 1~2일 전에 끝난다).

### 공고일 기준 절차

```
1) onbid_notice_list 로 공고를 넓게 받는다
   cltr_type_cd="0001", prpt_div_cd="0003,0005,0007"
   opbd_dt_start = 내일,  opbd_dt_end = 6개월 뒤     ← 개찰일 창은 넓게
   num_of_rows=1000, 끝까지 페이징
2) 응답의 pbancYmd(공고일)가 원하는 구간(예: 최근 7일)인 행만 남긴다
   → 그 행들의 onbidPbancNo 집합 = 「신규공고집합」
3) onbid_realestate_list 로 물건을 받는다 (규칙 0-1)
4) 물건의 onbidPbancNo 가 「신규공고집합」에 있는 것만 남긴다
5) lctnSggnm 으로 지역 필터, dspsMthodNm == "매각" 만,
   (cltrMngNo, pbctCdtnNo) 로 중복 제거
6) 물건에 공고일·공고명·집행기관을 붙인다
```

원 작성자 실측에서는 이 방식으로 뽑은 신규 물건의 거의 전부(99% 이상)가 아직 입찰 마감 전이었다. 개찰일 기준(전부 마감)과 정반대 결과다. [출처확인]

압류재산 공고 1건 안에 물건이 수백 건 들어 있을 수 있다(규칙 0-3). **지역 판정은 공고명이 아니라 물건의 `lctnSggnm` 으로 한다.**

---

## 규칙 0-3: 압류재산 공고는 「지역본부 × 차수」 묶음이다

| | 기타일반재산 0005 | 압류재산 0007 |
|---|---|---|
| 공고 단위 | **물건 1건 = 공고 1건** | **지역본부 × 차수 묶음** |
| 공고명 예 | `[개별매각] ○○시 ○○동 000-00 다세대주택` | `(○○지역본부) 2026년 제000차 압류재산 공매공고` |
| 주소 | 있음 | **없음** |
| 공고 1건의 물건 수 | 1건 | 수십~수백 건 |

- 공고명에서 구·시 이름을 찾는 방식은 **압류재산에 통하지 않는다.** 괄호 안 지역본부명(서울동부·서울서부·경기·인천·부산·대구경북·대전충남·광주전남·전북·강원·충북·경남)으로 대략 가를 수는 있지만, **물건 단위로 내려가 `lctnSggnm` 을 쓰는 것이 정확하다.**
- 지역본부 관할과 물건 소재지는 다를 수 있다(예: 인천지역본부 공고 안에 경기도 물건). [출처확인]

### 결과 API에서 압류재산이 안 잡히는 이유

`get_public_auction_items` 로 미래 개찰 구간을 보면 압류재산이 **전부 `취소`** 로 나오고, 대부분 주소가 마스킹(`○○시 ○○군 *****`)돼 있다. 낙찰·취소를 거르면 0건이 된다.
→ 입찰 가능한 압류재산은 결과 API로 잡지 말고 `onbid_realestate_list` 를 쓴다.

## 절대 규칙

### 규칙 1: 필수 파라미터

| 도구 | 필수 |
|---|---|
| `get_public_auction_items` / `onbid_notice_list` | `cltr_type_cd` · `prpt_div_cd` · `opbd_dt_start` · `opbd_dt_end` |
| `onbid_realestate_list` | `prpt_div_cd` · **`pvct_trgt_yn`** |

도구 설명에는 "선택(Optional)"으로 적혀 있어도 API는 필수로 요구한다. [출처확인]

### 규칙 2: 재산유형코드는 v2 신코드만

v1 구코드(`0101`, `0201`, `0301`)는 **오류 없이 `total_count: 0`** 을 돌려준다. 디버깅이 어려운 함정이다.

### 규칙 3: 불필요한 선택 파라미터를 추가하지 않는다

오류가 나도 다음 파라미터를 **임의로 넣지 않는다** — 결과가 과도하게 걸러진다.
`dsps_mthod_cd` · `bid_div_cd` · `pbct_stat_cd`
낙찰·유찰 구분이 필요하면 **전부 받은 뒤 `pbctStatNm` 으로 거른다.**
※ 예외: `onbid_realestate_list` 의 `pvct_trgt_yn` 은 필수다(규칙 0-1).

### 규칙 4: 날짜 형식은 yyyyMMdd 8자리

- 정상: `"20260504"`
- 금지: `"2026-05-04"`, `"2026/05/04"`, `"20260504 1100"`(시간 포함)
- 응답의 `cltrOpbdDt` 는 12자리(시간 포함)지만, 요청은 8자리만 쓴다.

### 규칙 4-1: 날짜 값 끝에 공백 1칸

숫자만 넣으면 도구 실행 환경이 **정수로 바꿔** `Input should be a valid string` 오류가 나는 경우가 있다. [출처확인]
- 해결: **값 끝에 공백 1칸** → `"20260531 "`. API가 공백을 잘라내므로 결과는 같다.
- **앞 공백은 0건을 돌려준다.** 반드시 **뒤**에 붙인다.
- 날짜를 빼면 기본값이 "최근 3개월"이라 **미래 개찰분이 통째로 빠진다.**

### 규칙 4-2: 지역 파라미터 이름

- `get_public_auction_items` 는 **`lctn_sdnm` / `lctn_sggnm`** 이다. `sido`·`sgk` 같은 이름을 쓰면 **오류 없이 무시되어 전국 120,000건 안팎이 돌아온다.** 첫 응답의 `total_count` 가 100,000건 단위면 이름을 틀린 것이다.
- 시도명은 공식 전체 이름: `"서울특별시"`, `"경기도"`, `"강원특별자치도"`, `"전북특별자치도"`.
- `get_public_auction_items` 의 `lctn_sggnm` 은 **시 단위까지만** 넣는다. `"용인시 기흥구"` 처럼 구를 붙이면 0건이다.
- `onbid_realestate_list` 는 `lctn_sggnm` 을 넣지 말고 응답 `lctnSggnm` 으로 거른다.

### 규칙 5: 통계 목적이면 지역 필터를 쓰지 않는다

`get_public_auction_items` 에 지역 필터를 걸면 **과거 개찰 건이 대량 누락된다.** [출처확인]

| 조회 | 12개월 | 최근 3개월 | 최근 3개월 비중 |
|---|---:|---:|---:|
| 전국 (필터 없음) | 163,360 | 43,544 | 26.7% (정상) |
| 경기도 (시도 필터) | 5,511 | 4,196 | **76.1% (과거분 소실)** |

원인: 압류재산의 절반 이상이 **주소 마스킹** 때문에 지역 색인에서 빠진다.
- 한두 건 찾기 → 지역 필터 사용 가능
- 낙찰가율 등 **통계 → 지역 필터 금지**. 전국으로 받은 뒤 물건명을 파싱한다.
- 지역 필터를 쓴 통계를 보여줄 때는 **선택편향이 남아 있다**고 결과에 적는다.

|---|---:|---:|---:|---:|
| 압류재산(0007) | 1,542 | 18,102 | 23,900 | 7.8% (**취소율 54.9%**) |

압류재산은 체납자가 세금을 내면 공매가 취소되므로 절반 이상이 취소된다. "다음 회차까지 기다릴까"를 판단할 때 **취소될 가능성**도 함께 본다.

## 페이지·응답 한계

| 항목 | 내용 |
|---|---|
| `num_of_rows` 상한 | **5,000** (10,000을 요청하면 빈 응답) |
| 깊은 페이지 | 정상 동작 |
| `totalCount` | 정확 |

- 모든 페이지를 받을 때까지 `page_no` 를 올린다. 첫 페이지만 보고 결론 내지 않는다.
- 페이지 도중 `num_of_rows` 를 바꾸면 중복·누락이 생긴다. 한 번 정한 값으로 끝까지 받고 `(cltrMngNo, pbctCdtnNo)` 로 중복을 제거한다.
- 응답이 크면 도구가 파일로 저장했다고 알려줄 수 있다. 그때는 **알려준 경로를 그대로** 쓰고, 최근 파일을 추측해서 집지 않는다.

### 타임아웃이 날 때

`API server timed out` 이 나면 **기간 → 지역 → 행 수** 순으로 줄인다.
- 전국 1년치를 한 번에 받지 말고 **월 단위로 나눠** 받는다.
- 한 페이지 행 수를 줄여 여러 페이지로 받는다.
- 단, 통계 목적이면 지역을 좁히지 말고 기간을 쪼갠다(규칙 5).

## 응답 필드 해석

### 회차 관련

| 필드 | 실제 의미 | 주의 |
|---|---|---|
| `usbdNft` | **유찰 횟수** | `onbid_realestate_list` 에 있다. 있으면 이것을 그대로 쓴다 |
| `feeRate` | 저감률(%) | 압류재산은 회당 10% 저감이라 `feeRate ÷ 10` = 유찰 회차 [추정] |
| `pbctNsq` | 0005는 **실제 회차** / 0007은 **캠코 연간 공매 차수**(예: `"033"`) | 0007에서 유찰 횟수로 쓰면 전부 틀린다 |

### 0005(기타일반재산)의 최저가율로 물건의 「나이」를 추론하지 않는다

0005는 최저가가 **채권액 기준**이라 감정가와 연동되지 않는다. [출처확인]
- **1회차부터 감정가의 100% 미만**인 물건이 있다(예: 57.5%)
- **감정가를 넘는** 최저가도 있다(예: 120.0%)
- **하루에 여러 회차를 연속 저감**하는 신탁 공고도 있다

→ "최저가율 90% 미만 = 오래 유찰된 물건"은 틀린 추론이다. 재공고 여부는 **회차 이력**으로 판단한다.
→ 물건관리번호 앞 4자리는 **온비드 최초 등록 연도**다. `2023-...` 번호가 새 공고로 다시 나오는 것은 정상이다.

### 입찰상태 (pbctStatNm)

- 결과 API: 유찰 / 낙찰 / 입찰마감 / 수의계약가능 / 취소 / 개찰중 [출처확인]
- `onbid_realestate_list` 는 추가로 `입찰준비중` · `입찰진행중` 을 돌려준다.

| 값 | 읽는 법 |
|---|---|
| 입찰준비중 / 입찰진행중 | **지금 입찰 가능**. 결과 API에는 없다 |
| 유찰 | 다음 회차 검토 후보 |
| 취소 | 압류재산 미래 회차는 결과 API에서 전부 이 상태로 보인다 |
| 수의계약가능 | 유찰이 반복된 뒤 협의 매수가 가능한 상태 |
| 개찰중 | 아직 낙찰이 아니다. **낙찰로 분류하지 않는다** |

처음 보는 값이 나오면 임의로 버리지 말고 **남겨 두고 보고**한다.

### 금액·면적 필드

| 필드 | 의미 |
|---|---|
| `apslEvlAmt` | 감정평가액 |
| `lowstBidPrcIndctCont` | 최저입찰가 (**문자열**로 온다 — 숫자로 바꿔 계산) |
| `scfbAmt` | 낙찰가 |
| `vldBddrNope` | 유효 응찰자 수 |
| `lowstBidCtrsScfbPrcRto` | 최저가 대비 낙찰가율 |
| `apslPrcCtrsScfbPrcRto` | 감정가 대비 낙찰가율 |
| `landSqms` · `bldSqms` | 토지·건물 면적 |
| `onbidCltrNm` | 물건명(주소 포함. 압류재산은 결과 API에서 마스킹 많음) |

### 응답 해석 예시 (가상의 값)

```json
{
  "apslEvlAmt": 400000000,
  "lowstBidPrcIndctCont": "80000000",
  "feeRate": 80,
  "pbctStatNm": "낙찰",
  "scfbAmt": "100000000",
  "apslPrcCtrsScfbPrcRto": 25.0,
  "vldBddrNope": 4
}
```

- 감정가 400,000,000원, 저감률 80%(최저가가 감정가의 20%인 80,000,000원)에서 낙찰 [출처확인: 응답값]
- 압류재산이라면 유찰 약 8회로 읽을 수 있다 [추정: feeRate ÷ 10]
- 4명이 경쟁해 최저가의 125%인 100,000,000원에 낙찰됐지만, 감정가 대비로는 25.0%다.
- 낮은 낙찰가율에는 보통 이유(권리 하자, 지분, 맹지, 점유 문제 등)가 있다. 숫자만 보고 싸다고 판단하지 않는다.

## 오류·조용한 실패 진단표

「오류 없이 0건」이나 「이상하게 많은 건수」가 가장 위험하다. **0건을 곧바로 "물건 없음"으로 보고하지 않는다.** 아래 원인을 하나씩 지운 뒤에만 "해당 조건의 물건이 없다"고 말하고, 그때도 [출처확인]과 함께 조회 조건을 적는다.

| 증상 | 원인 | 해결 |
|---|---|---|
| `NO_MANDATORY_REQUEST_PARAMETERS_ERROR`(코드 11) | 필수 파라미터 누락(규칙 1). `onbid_realestate_list` 라면 십중팔구 `pvct_trgt_yn` | 필수 항목만 채운다. 다른 파라미터를 이것저것 추가하지 않는다. 도구를 고장으로 판정하지 않는다 |
| `Input should be a valid string` | 날짜를 숫자만으로 넣었다 | 값 **뒤에** 공백 1칸 (규칙 4-1) |
| `total_count` 가 100,000건 단위 | 지역 파라미터 이름이 틀려 무시됐다 | `lctn_sdnm` / `lctn_sggnm` (규칙 4-2) |
| `total_count: 0` (오류 없음) | ① 구코드(0101 등) ② `0006`·`0011` ③ `num_of_rows` 5,000 초과 ④ 시군구에 구를 붙였다 ⑤ 날짜 **앞**에 공백 ⑥ 날짜 형식에 하이픈·슬래시 | 하나씩 확인 후 재조회 |
| 온비드 화면에 있는 물건이 응답에 없다 | 결과 API는 개찰 전 회차를 주지 않는다(규칙 0) | `onbid_realestate_list` 로 확인 |
| 압류재산이 하나도 안 나온다 | 개찰일 기준으로 보고 있다. 2주 개찰 주기 사이엔 0건이 정상(규칙 0-2·0-3) | 공고일 기준 + `onbid_realestate_list` |
| "신규"라는데 입찰이 이미 끝났다 | 개찰일 기준으로 신규를 잡았다 | 공고일 기준(규칙 0-2) |
| 과거 데이터가 이상하게 적다 | 지역 필터를 걸었다(규칙 5) | 전국으로 받아 파싱 |
| 읍면동으로 걸렀더니 일부 빠진다 | 법정동·행정동 차이 | 시군구로 받아 물건명으로 거름(템플릿 D) |
| `API server timed out` | 요청 범위가 너무 크다 | 기간을 월 단위로 쪼개고 행 수를 줄인다 |
| `SERVICE KEY IS NOT REGISTERED ERROR`(코드 30) / HTTP 403 | 인증키 미등록·만료, 또는 해당 서비스 활용신청 미승인 | data.go.kr 마이페이지에서 활용신청 상태와 키를 확인하도록 안내한다. 키 값을 채팅에 붙여 달라고 하지 않는다 |
| resultCode 12 | 폐기된 서비스 | 위 「쓸 수 없는 도구」 참고 |

### 잘못된 대응의 예

오류 코드 11을 받고 `dsps_mthod_cd`, `bid_div_cd`, `pbct_stat_cd` 를 차례로 추가해 보는 것은 해결이 아니다. 오류가 그대로이거나, 오류가 사라져도 결과가 몰래 좁아진다. **필수 항목부터 확인한다.**
